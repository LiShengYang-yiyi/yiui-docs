# 1.3 日志与排障

> **一句话**：运行时问题第一站是 `Logs/`（服务端）和 Unity Console（客户端）；编译期问题看分析器错误码 `ET0102` / `ET0105`。

**关键词**：日志 · Logs · Unity Console · 分析器 · ET0102 · ET0105 · 排障顺序

**目标**：拿到一个错误，知道该去哪一层的资料里找原因，而不是从头猜。

## 日志在哪

| 日志 | 位置 | 覆盖什么 |
|---|---|---|
| 服务端日志 | `Logs/` | 起服、协议处理、Scene 流转、异常 |
| 客户端日志 | Unity Console | UI 生命周期、资源加载、表现层异常 |
| 编辑期日志 | Unity Console | 资源导入、预制体、编辑器工具 |

> 启动服务器前先清空 `Logs/`。旧日志混在里面时，「最后一条 Error」可能来自上一次运行——这是排查中最常见的自伤。

## 把错误分成三类

排障的第一步不是看错误内容，是**先确定它属于哪一类**：

| 类别 | 出现时机 | 去哪查 |
|---|---|---|
| **编译期** | `dotnet build` / F6 | 分析器错误码，见下 |
| **启动期** | 服务端起不来、客户端连不上 | `Logs/` + [1.1](./1-build-and-start-server) 的四条硬约束 |
| **运行期** | 能起来但表现不对 | `Logs/` 找第一条 Error，再往上翻它之前的调用 |

## 编译期：分析器错误码

ET 的 SourceGenerator 会在编译时校验包之间的依赖与分层。两个最常撞到的：

| 错误码 | 含义 | 修法 |
|---|---|---|
| `ET0102` | 包调用了未声明的依赖包的方法 | 在调用方包的 `package.json` 的 `dependencies` 里加上被调用包 |
| `ET0105` | 包访问了未声明的依赖包的类型 | 同上 |

**这类错误不是代码写错了，是依赖没声明**。修的地方是 `package.json`，不是 `.cs` 文件。

排查步骤：

1. 从错误信息里提取**源包名**（`Package '...'`）和**目标包名**（`from package '...'`）；
2. 打开 `Packages/<源包>/package.json`；
3. 检查 `dependencies` 是否包含目标包；
4. 没有就加上，版本号参考目标包自己的 `package.json`；
5. 重新编译验证。

> 特殊情形：如果目标包**在本地不存在**（被裁掉或没装），加依赖也解决不了——要回头确认这个包该不该有。本工程已知有这种情况，见 [3.3 包依赖](./../3-code-layout/3-package-dependencies)。

## 运行期：按这个顺序看

1. 清空 `Logs/` → 重跑一次
2. `Logs/` 里搜 `Error` → 找**第一条**，不是最后一条
3. 从第一条 Error 往前翻 20~30 行，看它是在什么上下文里发生的
4. 定位到模块后，再去对应的包 `AGENTS.md` 看有没有已知约束

> 「第一条」比「最后一条」有用：错误会连锁，最后一条往往只是被牵连的受害者。
