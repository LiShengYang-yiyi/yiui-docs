# 2.2 组件式设计

> **一句话**：ET 放弃继承体系，用「数据（Component）+ 逻辑（System）」组合——组件可热插拔，逻辑放热更层，改 bug 不用重新发版。

**关键词**：组件式 · 组合替代继承 · 热插拔 · 数据逻辑分离 · System · 热更新

**目标**：理解「为什么 ET 的类里几乎没有方法」，以及这样组织带来的实际收益。

## 面向对象为什么在这里不适用

`Book/4.1` 用三个问题说明继承体系在游戏逻辑上的失效：

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **数据结构耦合极强** | 往父类加/删一个字段，会波及所有子类。游戏逻辑变化频繁，每次都要重排继承树 |
| 2 | **难以热插拔** | 继承和接口都是「粘上就甩不掉」。玩家下坐骑之后，坐骑的数据与接口还在身上 |
| 3 | **方法与数据耦合** | 类越写越大，出现上万行的虚函数，极难重构 |

第 3 条还会催生一个副作用：为了解耦而大量抽接口，代码里到处是接口，反而更难读。

## 组件模式的三个特点

1. **高度模块化**——一个组件 = 一份数据 + 一段逻辑
2. **可热插拔**——需要就加上，不需要就删掉
3. **依赖极少**——任何类型增删组件，不会影响其它类型

Unity 和虚幻都在客户端用这套。ET 的额外一步是：**把组件的「逻辑」也剥出去**，只留数据。

## ET 的做法：数据在 Entity，逻辑在 System

```
定义（数据）  →  Packages/<包>/Scripts/Model/    →  ET.Model 程序集
逻辑（System）→  Packages/<包>/Scripts/Hotfix/   →  ET.Hotfix 程序集
```

这样拆带来三个直接后果：

| 后果 | 意义 |
|---|---|
| 热更程序集只含逻辑 | 修 bug 可以通过热更完成，不用重新发版 |
| 一个组件的能力可以分散在多个 System 文件里 | 不用为了加一个功能去改类本身 |
| 组件可以随便挂 | PN 挂 `MoveComponent`，NPC 需要移动也挂同一个，不想要就不挂 |

一个典型例子：玩家需要移动、背包、技能、Buff，就挂四个组件；NPC 只需要移动和技能，挂两个即可——**不需要为 NPC 单独设计一套继承关系**。

## 一个容易被忽略的收益

因为组件是可拆卸的，ET 可以把**所有服务端组件装进同一个进程**：

- LoginServer 挂内网 + 外网网络组件
- BattleServer 只挂内网（外网消息由 Gate 转发）

结果是：平常开发用**一个进程**调试整套「分布式服务器」，发布时再拆成多个进程。

这不只是省事——它让分布式服务器的断点调试成为可能，这也是 ET 在工程上最有价值的设计之一。
