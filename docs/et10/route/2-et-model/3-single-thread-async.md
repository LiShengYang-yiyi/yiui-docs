# 2.3 单线程异步

> **一句话**：异步不等于多线程。ET 的业务逻辑跑在**单线程**上，用 `await` / `ETTask` 表达异步——所以不需要锁，但 `await` 之后必须用 `EntityRef<T>` 重新拿实体。

**关键词**：异步 · 协程 · ETTask · 单线程 · EntityRef · ETCancellationToken · NewContext

**目标**：理解「为什么异步不需要多线程」，以及 `await` 前后代码的安全边界。

## 三步演进

| 阶段 | 写法 | 问题 |
|---|---|---|
| 1. 回调 | 把后续逻辑写进回调函数 | 逻辑一多就变成回调地狱，插入/调整极易出错 |
| 2. `async` / `await` | 用语法把回调改成同步形式 | 写法好了，但**仍然默认会开线程** |
| 3. 单线程异步 | 所有回调在主线程的循环里驱动 | 没有线程切换，也没有竞态 |

第 3 步是整个设计的关键。做法是：异步操作只**登记**「等什么、等到后调谁」，然后由一个主循环每帧检查谁到期了，到期就在**主线程**里执行回调。

**结论：`await` 本身不会开新线程。** 用不用多线程，取决于被 await 的那个实现——在 ET 里，绝大多数实现都是单线程的。

## 单线程带来的直接好处

| 好处 | 说明 |
|---|---|
| 不需要锁 | 不会有两个逻辑同时改同一份数据 |
| 没有竞态 | 逻辑的推进顺序是确定的 |
| 断点可调试 | 不需要在线程之间跳 |
| 状态可推理 | 「这一刻数据是什么」永远只有一个答案 |

代价是：**一段逻辑如果卡住（同步阻塞），整个进程都卡住**。所以不能在业务代码里做同步 IO 或长时间 Sleep。

## ET 的落地写法

| 概念 | 用途 |
|---|---|
| `ETTask` / `ETTask<T>` | 替代 `Task`，单线程语义的 awaitable |
| `EntityRef<T>` | 跨 `await` 安全地持有实体引用 |
| `ETCancellationToken` | 协程取消 |
| `NewContext(...)` | 开一个独立协程 + 取消边界 |

### ⭐ `await` 之后的实体访问规则

这是 ET 异步代码里最容易出错的一点，规则很硬：

> **只要 `await` 之后还要访问实体，就在 `await` 前用 `EntityRef<T>` 拿引用，`await` 之后再取回来。**

原因：`await` 期间实体可能已经被销毁、或者被对象池回收后分配给了别人。直接继续用旧引用，读到的是**别人的数据**（而且不会报错）。这就是 [2.1](./1-everything-is-entity) 里 `InstanceId` 的作用——`EntityRef<T>` 是它的封装。

配套约定：

| 场景 | 做法 |
|---|---|
| 函数参数传实体 | 可以直接传 `Entity` |
| 字段 / 属性 / 集合里长期保存 | 存 `EntityRef<T>`，**不要**长期持有 `Entity` |
| 需要结果 | 在消费结果的协程里直接 `await`，不要返回句柄延后 await |
| 取消与协程边界 | 用 `NewContext(...)`；它不负责携带实体 |

### 什么时候**不该**用异步

不是所有逻辑都需要 `async`。只有真实等待资源的场景才保留：RPC、IO、定时器、协程锁、跨纤程取结果。

**如果调用方不依赖返回值，优先改成同步方法、普通消息、`Send` 或独立协程。** 无意义的 `async` 会凭空制造出「实体可能已失效」的窗口。
