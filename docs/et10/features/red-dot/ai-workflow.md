# 新增红点

> 用户只说一句「这里加个红点」时不能直接开改。必须先按固定顺序把缺失信息补齐，再决定改动范围。

**关键词**：新增红点 · 工作流 · 稳定层级 · 动态末级 · 只改配置 · ERedDotKeyType 三处同步

## 1 判断顺序

### 第一步：先判断是哪一类红点

至少先分清：

- 奖励可领取型
- 重要信息待查看型
- 阈值状态提醒型

同时还要判断：这是**稳定聚合层级**还是**动态末级对象**。

如果是动态末级对象，默认**不要新增枚举 key**，而是由上一级稳定节点承接红点数量或状态。

### 第二步：判断是新增节点还是复用已有节点

必须先查现有树：

- `Scripts/Model/Share/ERedDotKeyType.cs`
- `Assets/GameRes/RedDot/RedDotKeyAsset.asset`
- `Assets/GameRes/RedDot/RedDotConfigAsset.asset`

不要因为用户没说，就默认要新建 key。

### 第三步：判断这次是不是「只改配置」

必须明确属于哪一种：

| # | 范围 |
|---|---|
| 1 | 只需补 key 和父子关系 |
| 2 | key + 配置 + 业务触发 |
| 3 | key + 配置 + 已查看状态 |
| 4 | key + 配置 + UI 监听 |

需求里出现下面这些词时，通常**不是**只改配置：

`已读` · `已查看` · `打开过` · `切换过` · `领取后` · `阈值恢复后`

判断依据：只要有「已查看态 / 已领取态 / 未读态 / 阈值判断」，就必须有状态承载，见 [职责边界](./#_5-职责边界)。

### 第四步：按 ID 规则分配新 key

规则见 [Key 与 ID 编码规则](./#_3-key-与-id-编码规则)。同时记住：key 只加到稳定层级，不要给「未知数量、动态生成、运行时变化的具体对象」硬加固定 key。

### 第五步：至少同步这 3 处

新增 key 时最少同时修改：

1. `Scripts/Model/Share/ERedDotKeyType.cs`
2. `Assets/GameRes/RedDot/RedDotKeyAsset.asset`
3. `Assets/GameRes/RedDot/RedDotConfigAsset.asset`

只改其中 1~2 处，通常就是半残状态。

### 第六步：改了 `.cs` 必须编译验证

```powershell
powershell -ExecutionPolicy Bypass -Command "& 'Packages/cn.etetet.yiuimcp/Config/compile-unity-flow.ps1' -Force 0"
```

不能拿 `dotnet build` 替代。

## 2 必须先补出的判断

用户没说清时，至少要自己先回答这 8 个问题：

1. 红点挂在哪个父节点下
2. 它是聚合节点还是叶子节点
3. 客户端真实状态来源是什么
4. 红点亮起条件是什么
5. 红点消除条件是什么
6. 是否需要「已查看态」
7. 是否已有现成业务组件承接这个状态
8. 这次红点数量是谁算，算完由谁调用赋值

消除条件的常见类型：领取后消失 / 已读后消失 / 打开后消失 / 切换查看后消失 / 阈值恢复后自动消失。

## 3 不允许做的事

| 不允许 | 原因 |
|---|---|
| 把 `MessageObject` 当红点临时状态 | 红点数值只由 `RedDotData` 承载，别的实体一律不接 |
| 把业务状态塞进 YIUI Panel / View | UI 只负责表现，不负责业务缓存 |
| 看见「打开界面时请求」就让 UI 自己发协议 | 要落到客户端业务组件里，由组件控制是否请求、是否节流、是否缓存 |
| 为了快，直接跳过 `ERedDotKeyType` | 运行时 key 来源就是它，绕不过去 |
| 在 UI 打开时临时计算业务红点 | 会把业务、红点、UI 三层搅在一起，后面一定失控 |
| 给动态末级对象硬声明固定 key | 数量未知、生命周期不稳定，会拖乱枚举体系 |
| 一上来把所有细粒度节点拍满 | 红点树要先保证层级正确再补叶子，否则父级设计错了要全部返工 |

「在 UI 打开时临时计算」的两种典型错误方向：

- 打开任务面板时顺手遍历任务列表，再决定 `任务_主线` 红点有几个
- 刷任务 item 预制体时顺手回推某个父级红点数量

正确方向：

- 任务系统数据层在任务变化时计算主线红点数量
- 计算完成后统一调用红点赋值
- UI 打开时只读取红点结果并显示

## 4 回复用户时的最小结构

1. 这次红点归属的树位置
2. 这次是否新增 key
3. 新 key 的建议 id 与描述
4. 这次只改配置还是还要补业务状态
5. 后续验证方式

## 5 一个合格的例子

用户说：**「邮件有未读或附件没领时，菜单那里要亮」**

不应直接答「我去加个红点」，而应先得出：

1. `菜单` 已有二级节点
2. `菜单_邮件` 已有三级节点
3. 如果只是菜单入口聚合，可能复用 `菜单_邮件`
4. 若要更细粒度，还需要叶子，如 `菜单_邮件_未读邮件`、`菜单_邮件_附件可领取`
5. **这不是纯配置问题**——邮件状态要来自客户端邮件业务组件

这才是一次完整的判断。
